# Автоматический деплой из GitHub

Workflow: [ci-deploy.yml](../../.github/workflows/ci-deploy.yml).

| Ветка | GitHub environment | Сайт | Каталог VPS |
| --- | --- | --- | --- |
| `main` | `production` | https://do.lensws.be | `/opt/opendoist/prod` |
| `beta` | `beta` | https://beta.lensws.be | `/opt/opendoist/beta` |

## Что происходит при push

1. GitHub-hosted runner получает точный commit SHA и устанавливает Node.js 24 и зависимости через `npm ci`.
2. Выполняет `npm test`, проверяет синтаксис скриптов и собирает Docker-образ.
3. Повторяет тесты внутри production-образа. Ошибка любого шага блокирует деплой (`needs: test`).
4. Job `deploy` получает SSH-ключ только своего GitHub environment и передаёт на VPS проверенный SHA.
5. Сервер проверяет ветку и актуальность SHA, последовательно собирает образ, сохраняет SQLite backup, заменяет контейнер и проверяет healthcheck и HTTPS.

Pull request запускает проверки без деплоя и без доступа к environment secrets. Workflow можно также запустить вручную через Actions → Test and deploy → Run workflow, выбрав `main` или `beta`.

Публикация новой версии требует успешного workflow; сам push ещё не означает завершённый деплой. Состояние доступно во вкладке [Actions](https://github.com/lensws/opendoist/actions) и GitHub environments.

## Работа с ветками

Разрабатывайте изменения в `beta`; push автоматически обновит тестовый сайт после тестов. Владелец проверяет сайт и пишет в чате «выкатывай на основной». Только после этого агент переносит проверенный коммит в `main`. Проверки на `main` выполняются заново, затем обновляется основной сайт. PR и environment approval не требуются. У веток отдельные данные, пароли и контейнеры.

Workflow не прерывает уже начатую выкладку. Дополнительно `flock` на VPS сериализует сборки prod и beta, чтобы не перегружать сервер с 1 ГБ памяти. Если к моменту начала серверного деплоя SHA уже не является вершиной соответствующей ветки, старая выкладка пропускается — новый push имеет свой workflow.

## Доступ и секреты

В каждом GitHub environment настроены:

- `VPS_SSH_KEY` — свой приватный Ed25519-ключ.
- `VPS_KNOWN_HOSTS` — закреплённый публичный ключ VPS, проверка SSH-хоста обязательна.
- Branch deployment policy: только `main` для `production`, только `beta` для `beta`.

Пароли приложения остаются в `.env` на VPS и не передаются в GitHub. SSH-пользователь `opendoist-deploy` не входит в группу Docker. В `authorized_keys` каждый ключ привязан к своей ветке через forced command, без PTY, forwarding и произвольной shell-сессии. Wrapper принимает только 40-символьный hex SHA. Sudo разрешает только отдельный root-owned deploy-скрипт, который повторно проверяет аргументы.

Установленные доверенные файлы:

- `/usr/local/bin/opendoist-ssh` ← `ssh-command.sh`;
- `/usr/local/sbin/opendoist-deploy` ← `deploy.sh`;
- `/etc/sudoers.d/opendoist-deploy`;
- `/home/opendoist-deploy/.ssh/authorized_keys`.

Эти серверные файлы не обновляются автоматически из репозитория. Изменения самого механизма деплоя нужно проверять и устанавливать по административному SSH отдельно. Изменение workflow или кода в разрешённой ветке может изменить поведение приложения на соответствующем сервере: выдавайте write-доступ к репозиторию только доверенным людям.

Для замены ключа сгенерируйте новую пару, обновите публичную строку с той же forced command на VPS и environment secret в GitHub. Не сохраняйте приватные ключи в репозитории. Изменение ключа самого VPS требует отдельно обновить `VPS_KNOWN_HOSTS` после проверки нового fingerprint.

## Ошибки, резервные копии и откат

До замены контейнера старый экземпляр продолжает работать. После замены возможен короткий перерыв на запуск — это не zero-downtime deploy.

Перед каждой выкладкой SQLite online backup копируется в `/var/backups/opendoist/prod/` или `/var/backups/opendoist/beta/`. Эти каталоги доступны root. Это резервные копии на том же VPS, не защита от потери всего сервера. Копируйте их на другое хранилище и контролируйте свободное место; автоматическое удаление старых копий не настроено.

При ошибке сборки/активации/healthcheck скрипт пытается вернуть предыдущие Git SHA и Docker image. База при автоматическом откате **не заменяется**: иначе можно потерять записи, сделанные после снимка. Если новая версия внесёт несовместимую миграцию схемы, может понадобиться ручное восстановление по [инструкции](../README.md#4-резервные-копии-и-восстановление). Сбой отката явно выводится в лог Actions. Глобальная блокировка и таймауты ограничивают параллелизм и зависание команд, но после обрыва связи статус сервера следует проверить вручную.

Для штатного отката сделайте revert проблемного изменения в соответствующей ветке и push: откат снова пройдёт тесты и обычный pipeline. Аварийное ручное переключение описано в [VPS.md](../VPS.md); последующий push в ветку снова запустит автоматический деплой.

## Первичная установка на новом VPS

Сначала установите два работающих экземпляра по [VPS.md](../VPS.md). Deploy-скрипт требует существующий контейнер и базу, чтобы сделать backup и иметь предыдущий образ для отката.

Установите root-owned скрипты, создайте пользователя `opendoist-deploy`, ограниченные ключи и sudoers по схеме выше. Создайте GitHub environments и их secrets, разрешите соответствующие ветки. Приватные ключи передавайте через GitHub Secrets, а не коммитом. Адрес VPS прописан в workflow; домены, каталоги и имена Compose-проектов — в доверенном серверном скрипте.

## Выпуск по команде владельца

1. Агент делает изменения в `beta` и дожидается успешного CI и beta-деплоя.
2. Владелец проверяет https://beta.lensws.be.
3. Владелец пишет в чате «выкатывай на основной» (или явно разрешает релиз другой формулировкой).
4. Агент проверяет, что одобренный SHA действительно развёрнут на beta, а его `Tests and Docker build` завершился успешно. Если после проверки владельца появились новые изменения, их нельзя включать в релиз без нового разрешения.
5. Агент переносит этот SHA в `main` fast-forward push, без force push. Затем ждёт повторных тестов, production-деплоя и успешного healthcheck.

В `main` остаётся обязательная проверка `Tests and Docker build` (GitHub Actions), включая для администратора, и запрет force push/удаления. Требования PR и `beta-review` сняты. Подтверждение владельца в чате — правило работы агента, а не техническая проверка GitHub: человек с правом записи может самостоятельно отправить уже прошедший проверки коммит в main.

Для агента порядок сохранён в [AGENTS.md](../../AGENTS.md). Само согласие изменить настройки CI/CD не является разрешением выпустить текущую beta. Если main не является предком одобренного SHA, нужно сначала согласовать ветки в beta, повторить тесты и проверку сайта, а не обходить ограничения.

GitHub не требует PR и нажатия Review deployments. Pull request остаётся необязательным инструментом обсуждения кода. При обычном выпуске агент не создаёт PR и не меняет настройки защиты веток.
