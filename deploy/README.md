# Развёртывание OpenDoist

Личное приложение: один пароль, одно пространство задач. Пароль задаётся на сервере; регистрации и сторонних провайдеров авторизации нет. Требуются Docker Engine и Docker Compose v2. Альтернатива — Node.js 24+ и `npm start` из корня проекта.

Для `do.lensws.be` и `beta.lensws.be` используйте [инструкцию двух окружений](VPS.md). Ниже — установка одного экземпляра на новый VPS.

## 0. Подготовка Ubuntu 24.04

Подключитесь по SSH. Следующие команды выполняются от root на чистом сервере:

```sh
apt-get update
apt-get install -y docker.io docker-compose-v2 caddy git ca-certificates
systemctl enable --now docker caddy
docker --version
docker compose version
```

На сервере должны быть доступны входящие TCP-порты 80 и 443 для HTTPS и выпуска сертификатов; сохраните доступ по SSH. Проверьте также firewall в панели VPS. Порт приложения 3000 открывать наружу не нужно. Если домен имеет AAAA-запись, IPv6 тоже должен вести на этот сервер и принимать HTTP/HTTPS.

## 1. Запуск

Получите исходники и закрепите конкретную версию. Команды ниже предназначены для новой установки; для существующей используйте раздел об обновлении.

```sh
mkdir -p /opt
git clone https://github.com/lensws/opendoist.git /opt/opendoist
cd /opt/opendoist
git checkout --detach "$(git rev-parse origin/main)"
```

Создайте конфигурацию:

```sh
cp .env.example .env
chmod 600 .env
```

В текстовом редакторе задайте `OPENDOIST_PASSWORD` — уникальный пароль от 12 символов. Значение-заглушку приложение не принимает. Если пароль содержит `$`, `#` или пробелы, заключите значение в одинарные кавычки в `.env`. Не включайте `.env` в Git.

Для локального доступа оставьте `PUBLIC_URL=http://localhost:3000` и `COOKIE_SECURE=false`.

```sh
docker compose up -d --build
docker compose ps
docker compose logs --tail=50 opendoist
```

Откройте `http://localhost:3000` и введите пароль. Если сервер удалён и домен ещё не настроен, используйте SSH-туннель:

```sh
ssh -L 3000:127.0.0.1:3000 user@your-server
```

Контейнер публикует порт только на loopback-интерфейсе сервера. Данные находятся в именованном томе `opendoist-data`; пересоздание контейнера их не удаляет. Контейнер работает от непривилегированного пользователя с корневой файловой системой только для чтения.

## 2. Доступ по домену и HTTPS

Направьте DNS домена на сервер. Установите Caddy на хосте и используйте пример из [Caddyfile](Caddyfile), заменив `tasks.example.com` на ваш домен. Caddy должен иметь доступ к портам 80/443 и будет проксировать запросы на `127.0.0.1:3000`. Пример рассчитан на Caddy **на хосте**, не в отдельном контейнере.

Обновите `.env`:

```dotenv
PUBLIC_URL=https://tasks.example.com
COOKIE_SECURE=true
```

Затем установите конфигурацию Caddy. На сервере с другими сайтами добавьте блок в существующий Caddyfile вместо замены всего файла.

```sh
cp deploy/Caddyfile /tmp/opendoist.Caddyfile
# Откройте /tmp/opendoist.Caddyfile в редакторе и замените домен.
caddy validate --config /tmp/opendoist.Caddyfile --adapter caddyfile
cp /etc/caddy/Caddyfile /etc/caddy/Caddyfile.before-opendoist
install -m 644 /tmp/opendoist.Caddyfile /etc/caddy/Caddyfile
docker compose up -d
systemctl reload caddy
```

Caddy автоматически получает и продлевает сертификат, а HTTP перенаправляет на HTTPS. После запуска проверьте `https://ваш-домен/healthz` и вход в приложение.

`PUBLIC_URL` должен совпадать с origin страницы в браузере (схема, домен, порт). Иначе запросы изменения данных будут отклоняться. Публикуйте приложение через HTTPS; прямой HTTP подходит для localhost/SSH-туннеля. При HTTPS Secure-cookie включается также автоматически по `PUBLIC_URL`.

Если используете свой nginx/Traefik, направьте его на тот же локальный порт, настройте TLS и передайте исходный `Host`. Приложение ожидает размещение в корне отдельного домена, без префикса пути.

## 3. Обновление и смена пароля

Сначала сделайте резервную копию. Выберите проверенный commit SHA в GitHub. В каталоге проекта:

```sh
git rev-parse HEAD  # сохраните текущий SHA для возможного отката
git fetch origin
# Подставьте выбранный SHA вместо <commit-sha>.
git checkout --detach <commit-sha>
docker compose up -d --build
docker compose ps
```

Push в GitHub сам по себе не обновляет сервер. `.env` и данные в томе сохраняются при обновлении исходников.

Данные сохранятся в томе. `docker compose down` оставляет том; **`docker compose down -v` удаляет его вместе со всеми задачами**.

Для смены пароля отредактируйте `.env` и выполните `docker compose up -d`. Старые сессии перестанут работать после пересоздания контейнера. Сессии действуют 7 дней, выход удаляет текущую сессию. Десять попыток входа за минуту блокируют новые попытки на оставшееся время окна; лимит общий для этого личного сервера.

## 4. Резервные копии и восстановление

JSON-экспорт доступен в интерфейсе; он содержит все текущие задачи и последние 100 выполнений. Это удобный переносимый файл, **не полная резервная копия**; встроенного импорта JSON пока нет.

Для полного снимка SQLite без остановки приложения:

```sh
mkdir -p backups
docker compose exec opendoist node server/backup.js /app/data/backup-2026-11-02.sqlite
docker compose cp opendoist:/app/data/backup-2026-11-02.sqlite backups/backup-2026-11-02.sqlite
```

Используйте новое имя с актуальной датой для каждого снимка. Скрипт не перезаписывает существующие файлы и использует SQLite online backup, учитывающий WAL. После копирования можно удалить снимок из тома, чтобы не занимать место. Храните копии отдельно от сервера: они содержат задачи и сессии доступа.

Без Docker:

```sh
node --env-file-if-exists=.env server/backup.js backups/backup-2026-11-02.sqlite
```

Для восстановления сначала остановите приложение и убедитесь, что выбран правильный файл. Следующие команды заменят текущую базу выбранным снимком:

```sh
docker compose stop opendoist
docker compose run --rm --no-deps --entrypoint sh opendoist -c 'rm -f /app/data/opendoist.sqlite-wal /app/data/opendoist.sqlite-shm'
docker compose cp backups/backup-2026-11-02.sqlite opendoist:/app/data/opendoist.sqlite
docker compose run --rm --no-deps --user root --entrypoint sh opendoist -c 'chown node:node /app/data/opendoist.sqlite'
docker compose start opendoist
```

После восстановления рекомендуется сменить пароль, чтобы аннулировать сессии из снимка. Не копируйте один основной `.sqlite` у работающего приложения вручную: свежие транзакции могут находиться в WAL.

## Настройки окружения

| Переменная | Назначение |
| --- | --- |
| `COMPOSE_PROJECT_NAME` | Постоянное имя окружения; для двух установок имена должны различаться |
| `OPENDOIST_PASSWORD` | Обязательный пароль, минимум 12 символов |
| `PUBLIC_URL` | Origin приложения; для production задавайте явно |
| `COOKIE_SECURE` | `true` при HTTPS |
| `PORT` | Порт хоста в Compose, порт HTTP-сервера при запуске напрямую; по умолчанию 3000 |
| `HOST` | Только прямой запуск: по умолчанию `127.0.0.1`; внутри Docker уже `0.0.0.0` |
| `DATABASE_PATH` | Только прямой запуск: по умолчанию `./data/opendoist.sqlite`; Docker использует том `/app/data` |

При изменении порта обновите также `PUBLIC_URL` и reverse proxy. Язык и часовой пояс новых задач выбираются в интерфейсе и сохраняются в браузере. Каждая задача хранит собственный часовой пояс на сервере.

## Проверка установки

`GET /healthz` возвращает `{"ok":true}`; Docker использует его для healthcheck. Откройте приложение, создайте задачу с повторением, выполните её и проверьте следующий срок. Перезапустите контейнер и убедитесь, что задача осталась. Исходный набор автотестов запускается командой `npm ci && npm test` на Node.js 24+.

Приложение рассчитано на один экземпляр сервера и локальный SQLite-том. Не запускайте несколько реплик с общей базой на сетевой файловой системе. Не реализованы команды, проекты, несколько пользователей, уведомления, офлайн-режим и автоматическая синхронизация между открытыми окнами; изменения в другом окне требуют обновить список/страницу. Конфликтующие записи защищены версиями задач.
